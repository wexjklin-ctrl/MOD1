ПЛАН РЕНДЕРА (следующий шаг): наш кэш хранит на колонку цвет верха, высоту и профиль стен (NW=16), но НЕ полные воксели. Поэтому делаем «heightfield raycast»: на каждый пиксель тайла 512x512 (x4 px/блок, 2x2 сэмпла) идём лучом камеры по высотной карте (v=z*sin-y*cos, шаг по z), находим первую колонку, чья высота выше луча; если луч входит в южную стену — цвет стены из профиля по глубине (side-цвет), иначе верх. Далее shade() как в Java: ламберт + тень солнца (марш по высотной карте к солнцу), AO по 4 углам из высот соседей, skyOcclusion, heightShade, контур по разнице глубины > 1.5, цветокоррекция (saturation/exposure/tints) в линейном свете. Выводить тайлами 128x128 блоков с кэшем (текстура на тайл), LOD через уменьшенные тайлы. Это даст стены/кубы/тени как в Java без полных вокселей. Для деревьев/зданий нужны высокие колонки с профилем (есть).

## Сессия 24: диагноз «смазанные постройки» (скриншоты владельца, Java vs наш)
Разрешение не причина: PPC=4 px/блок уже как в Java. Причина в МОДЕЛИ ДАННЫХ: у колонки есть только высота верхнего блока + цвет верха + профиль цветов вниз. Из этого нельзя восстановить:
- скаты крыш из ступеней/плит (в Java каждый блок даёт свои грани, у нас крыша = гладкие вертикальные полосы одного цвета);
- навесы, балконы, пустоты под крышей, заборы, двери, перила (всё, что не сплошной столб до земли);
- поблочные грани и текстурные акценты (Java берёт цвет по граням каждого блока).
Нужен НАСТОЯЩИЙ ВОКСЕЛЬНЫЙ путь (как GridRay/TileBaker в Java):
1. Хранение: на колонку список «прогонов» (yBottom, yTop, paletteId u16) непрозрачных/частичных блоков, палитра: id -> {top rgb, side rgb, shape flags (full/slab/stair/fence/pane)}; сохранять RLE (колонка леса/дома ~3-10 прогонов, ~100 Б вместо 128 Б профиля; НЕ хранить воздух).
2. Рендер: для каждого пикселя тайла луч камеры (pitch 50°) DDA по вокселям (порт GridRay.java), первая непустая ячейка -> грань (top/south/east/west не нужны по камере: top и south), цвет из палитры; для ступеней/плит учитывать половинку по Y (упрощённо: плита = верхний/нижний полублок). Затем тот же shade() (тень, AO, контуры).
3. Производительность: миникарта 4*224^2 лучей ок в фоне; большая карта — только тайлами 128x128 с кэшем + LOD (на дальних уровнях использовать старый heightfield).
4. Сканирование: BlockSource::getBlock по всем Y до ~96 блоков вниз от верха — тяжелее, делать по 1 чанку/кадр и приоритет ближним.
Это следующий крупный шаг; делать поэтапно: (a) структура VoxCol + сканер + сохранение, (b) рендер миникарты лучами с флагом режима, старый heightfield как запасной, (c) тайлы/LOD для большой карты.
- Сессия 25: ВОКСЕЛЬНЫЙ painter (коммит d3dbe1e, сборка зелёная, в игре НЕ проверено). ## Сессия 28: ПЛИТКИ + LOD для большой карты, блокировка ввода (в игре НЕ проверено)
Большая карта (M) теперь рисуется из мировых плиток (`drawTileMap`, Minimap.cpp, секции «seamless world tiles» и «tile manager»). Старый путь Slot[1]/gBigTex остался только запасным (прямоугольники при `gTexFailed`).
- Глобальная проекция: опорная высота kHRef=64, строка = KY*PPC = 3 px на z-ряд, подъём 2.52 px/блок. Плитка уровня 0: 128 блоков по X, 170 z-рядов (=510 px), контент 512x510 в текстуре 512x512. Окно запекания kBakeN=160 (640 px) вокруг центра плитки (cz = 170j+85), обрезка (64, 65) -> швов нет по построению.
- Запекание: отдельный поток `tileWorkerMain` вызывает `rasterize(..., painter=true)` (тот же painter, что у миникарты) для плитки; очередь по близости к центру вида (до 3 в очереди).
- LOD: уровень L = 2x2 box-фильтр детей (`contributeToParent`), те же 512x510 px, kLMax=3. Детали при отдалении НЕ упрощаются (дети запечены в полном качестве, уровни только уменьшают). Пока детальной плитки нет, рисуется кусок более грубого уровня (stand-in).

## Сессия 42: хранение под большие карты (в игре НЕ проверено)
- Регионы на диске: DBM7 = заголовок + один LZ4-блок (свой кодек lz4Compress/lz4Decompress в Minimap.cpp), рядом `r.X.Z.idx` (битовая карта 1024 чанков с данными). Старые DBM2..6 читаются; регионы без .idx догружаются по одному (gLegacyPending) и пересохраняются сжатыми.
- Ленивая загрузка: loadWorld НЕ читает чанки, только список файлов + .idx -> `gKnown` (множество известных чанков: туман, счётчик). Регион читается в gCache через `regionReady(rx,rz,true)` (1 регион на кадр) при скане около игрока и перед запеканием плитки (регионы окна плитки).
- Выгрузка: `pumpRegions()` каждый кадр; если регионов в RAM > kRegionCap(10) и пекари простаивают -> LRU-регионы сохраняются (если dirty) и удаляются из gCache. Запекание не планируется, пока регионов > cap+6.
- Плитки на диске: `tiles/t<L>.<i>.<j>.dtl`, LZ4 по байтовым плоскостям, формат kTileFmt=1 (ПОДНЯТЬ при любом изменении вида painter!). Сохраняются через 90 кадров после последнего изменения (1 за проход), грузятся по требованию (<=2 за кадр) в drawTileCell/заглушках; родитель подгружается с диска перед contributeToParent. initTilesFromCache пропускает плитки, которые уже есть на диске. Пиксели в RAM держим <=96 плиток (все уровни), если они сохранены и загружены на GPU.
- Туман: только gKnown (чанк известен -> туман уходит, с ожиданием плитки на зуме <=600 блоков).
- Сохранение dirty-регионов раз в 240 кадров (регион сжимается ~десятки мс).
Риски: синхронное чтение региона (подвисание на границе), миграция старых карт при первом заходе, плитки старого формата не нужны (их ещё не было на диске).
Следующее: GPU-запекание плиток (план в сессии 40).

## Сессия 43: дыры на дальнем зуме (в игре НЕ проверено)
Причина: на макс. отдалении рисуются плитки L>0, которые заполняются только по мере запекания L0-детей (или с диска); незапечённые участки -> прямоугольные дыры, а туман я в сессии 41 отключил на зуме >600 блоков (fogChunkReady обходился). Теперь: `gDrawL` = рисуемый уровень; fogChunkReady требует показанную плитку уровня >= gDrawL, а для L>0 ещё и что L0-ребёнок запечён и пропагирован (или лежит на диске). Туман остаётся над недопеченным. Пекари: 2-4 потока, сон 30% времени (было 1-3 / 60%) - быстрее заполнение.

## Сессия 44: GPU-освещение плиток (в игре НЕ проверено, включается `tilebake=1` в %APPDATA%\minimap2\gpu.txt)
Новый файл GpuBake.cpp: D3D12 compute (HLSL, cs_5_0), своя DIRECT-очередь, синхронный вызов `gpu::bakeShade` из потока пекаря (мьютекс). Устройство берётся из GpuHook (initCtx -> bakeSetDevice).
Разделение: CPU строит HField (sampleCell, sky) и «записи видимых точек» Rec на 4 сэмпла (paint far->near); GPU делает shading (AO, skyBilinear/skyAtHeight, inShadow 40 шагов, свет, градация sRGB, усреднение 4 сэмплов) в CS1 и контуры в CS2; обратно читаются px (0xAARRGGBB) и hb. Затем на CPU как раньше заливка дыр.
Только step==1 и W<=768, gn*m<=240000. Первые 2 плитки сверяются с CPU (лог «GPU tilebake check: mean difference ...»); если среднее >4 уровней или несовпадение покрытия >2% -> GPU отключается. Любая ошибка -> CPU-путь.
Что ещё на CPU: buildHField (выборка столбцов + sky 8x7 лучей), генерация Rec (paint). Следующие шаги: sky на GPU, paint на GPU (нужен gather с z-тестом или atomic по глубине), пул ресурсов под несколько одновременных заданий.
